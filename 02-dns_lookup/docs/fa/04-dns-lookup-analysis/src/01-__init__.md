## ۱. مقدمه

با بزرگ‌تر شدن برنامه‌های Python، قرار دادن تمام کدها در یک فایل، نگهداری و توسعه آن‌ها را دشوار می‌کند. به همین دلیل، معمولاً برنامه به چند ماژول تقسیم می‌شود که هرکدام مسئولیت مشخصی دارند.

برای مثال، یک ابزار DNS Lookup می‌تواند بخش‌های جداگانه‌ای برای اعتبارسنجی ورودی‌ها، ارسال درخواست DNS، پردازش نتایج، قالب‌بندی خروجی و ثبت گزارش‌ها داشته باشد.

<div align='right' dir='rtl'>

<span dir='rtl'>Python امکاناتی برای سازمان‌دهی این بخش‌ها در قالب **Module** و **Package** فراهم می‌کند.</span>

</div>

در این درس، با فایل <span dir='ltr'>`__init__.py`</span>، مفهوم import نسبی و نقش این فایل در سازمان‌دهی اعضای یک پکیج آشنا می‌شویم.

## ۲. ماژول و پکیج چه تفاوتی دارند؟

### ماژول (Module)

ماژول معمولاً یک فایل Python با پسوند <span dir='ltr'>`.py`</span> است که می‌تواند شامل توابع، کلاس‌ها، متغیرها و دستورات اجرایی باشد.

برای مثال، در پروژه DNS Lookup ماژول‌هایی با نام‌های زیر وجود دارند:

<div align='right' dir='rtl'>

<span dir='rtl'>• `validator.py`</span> <br>
<span dir='rtl'>• `resolver.py`</span> <br>
<span dir='rtl'>• `models.py`</span> <br>
<span dir='rtl'>• `formatter.py`</span> <br>
<span dir='rtl'>• `logger.py`</span>

</div>

هر ماژول بخشی از کد برنامه را در خود جای می‌دهد.

### پکیج (Package)

پکیج روشی برای سازمان‌دهی ماژول‌های مرتبط در یک ساختار مشترک است.

ساختار ساده‌شده بخش اصلی پروژه DNS Lookup به این شکل است:

```text
src/
├── __init__.py
├── validator.py
├── resolver.py
├── models.py
├── results.py
├── formatter.py
├── exporter.py
├── csv_exporter.py
├── logger.py
└── exception.py
```

در این ساختار، هر فایل Python یک ماژول مستقل است و <span dir='ltr'>`__init__.py`</span> می‌تواند نحوه دسترسی به بخش‌هایی از این ماژول‌ها را از طریق پکیج ساده‌تر کند.

این ساختار یک نمونه از تقسیم مسئولیت‌ها در پروژه است؛ جزئیات وظایف هر ماژول در درس‌های مربوط به همان فایل بررسی می‌شوند.

## ۳. فایل <span dir='ltr'>`__init__.py`</span> چیست؟

فایل <span dir='ltr'>`__init__.py`</span> برای مقداردهی اولیه یک پکیج معمولی Python استفاده می‌شود.

هنگامی که یک پکیج معمولی import می‌شود، کد سطح بالای این فایل اجرا می‌شود. این فایل همچنین می‌تواند نام‌های انتخاب‌شده‌ای را از ماژول‌های داخلی وارد کند تا دسترسی به آن‌ها از مسیر پکیج آسان‌تر شود.

در پروژه DNS Lookup، محتوای این فایل شامل importهای زیر است:

```python
from .validator import validate_domain, validate_timeout, validate_record_type
from .resolver import lookup_record
from .models import DNSRecord
from .results import build_dns_results
from .formatter import format_dns_results
from .exporter import export_json
from .csv_exporter import export_csv
from .logger import setup_logger
```

این کدها تعریف جدیدی از توابع یا کلاس‌ها ایجاد نمی‌کنند؛ بلکه نام‌های موجود در ماژول‌های دیگر را وارد فضای نام ماژول <span dir='ltr'>`__init__.py`</span> می‌کنند.

در نتیجه، این نام‌ها می‌توانند از طریق فضای نام پکیج نیز در دسترس قرار بگیرند.

## ۴. بررسی مفهوم Import نسبی

در کد بالا، نام ماژول‌ها با یک نقطه شروع می‌شود؛ مانند:

```python
from .resolver import lookup_record
```

این نقطه نشان‌دهنده **Relative Import** یا import نسبی است.

در این دستور:

<div align='right' dir='rtl'>

<span dir='rtl'>• `.` به پکیج جاری اشاره می‌کند.</span> <br>
<span dir='rtl'>• `resolver` نام ماژول داخلی است.</span> <br>
<span dir='rtl'>• `lookup_record` نامی است که از آن ماژول وارد می‌شود.</span>

</div>

بنابراین، این دستور نام `lookup_record` را از ماژول `resolver` در محدوده پکیج جاری وارد می‌کند.

### تفاوت با Import معمولی

در یک import معمولی می‌توان نوشت:

```python
import json
```

در این حالت، ماژول استاندارد `json` وارد می‌شود.

اما در import نسبی، رابطه میان ماژول‌های داخل یک پکیج به‌صورت صریح مشخص می‌شود.

### چرا Import نسبی مفید است؟

<p dir='rtl'>
Import نسبی کمک می‌کند وابستگی میان اجزای داخلی پکیج روشن باشد. همچنین از نیاز به نوشتن مسیرهای طولانی یا وابسته به نام‌گذاری بیرونی در بعضی ساختارهای پروژه جلوگیری می‌کند.
</p>

البته import نسبی به زمینه اجرای پکیج وابسته است. اجرای مستقیم یک فایل که از import نسبی استفاده می‌کند، ممکن است باعث خطای `ImportError` شود؛ زیرا Python در اجرای مستقیم فایل لزوماً زمینه پکیج را در اختیار ندارد.

## ۵. بررسی نام‌های واردشده در پکیج

در ادامه، نام‌هایی را بررسی می‌کنیم که در <span dir='ltr'>`__init__.py`</span> وارد شده‌اند.

### ۵.۱. توابع اعتبارسنجی

```python
from .validator import validate_domain, validate_timeout, validate_record_type
```

سه نام از ماژول `validator` وارد می‌شوند:

<div align='right' dir='rtl'>

<span dir='rtl'>• `validate_domain`</span> <br>
<span dir='rtl'>• `validate_timeout`</span> <br>
<span dir='rtl'>• `validate_record_type`</span>

</div>

این نام‌ها به‌ترتیب به اعتبارسنجی دامنه، Timeout و نوع رکورد اشاره دارند. اما برای مشخص شدن قواعد دقیق اعتبارسنجی، نوع خطاها و مقادیر قابل قبول، باید پیاده‌سازی ماژول `validator.py` بررسی شود.

### ۵.۲. تابع جست‌وجوی DNS

```python
from .resolver import lookup_record
```

نام `lookup_record` از ماژول `resolver` وارد می‌شود.

این نام به عملیات جست‌وجوی رکورد DNS اشاره دارد. نحوه ارسال Query، استفاده از Resolver و مدیریت خطاهای شبکه در خود ماژول مشخص می‌شود.

### ۵.۳. مدل رکورد DNS

```python
from .models import DNSRecord
```

نام `DNSRecord` از ماژول `models` وارد می‌شود.

نام آن نشان می‌دهد که با مدلی مرتبط با رکوردهای DNS سروکار داریم. فیلدهای دقیق، نوع تعریف کلاس و نحوه استفاده از آن باید در `models.py` بررسی شوند.

### ۵.۴. ساخت و قالب‌بندی نتایج

```python
from .results import build_dns_results
from .formatter import format_dns_results
```

این دو نام از دو ماژول متفاوت وارد می‌شوند.

<div align='right' dir='rtl'>

<span dir='rtl'>• `build_dns_results` با ساخت نتایج DNS مرتبط است.</span> <br>
<span dir='rtl'>• `format_dns_results` با قالب‌بندی نتایج مرتبط است.</span>

</div>

نام‌ها به ما درک اولیه‌ای از هدف این توابع می‌دهند، اما قرارداد دقیق ورودی و خروجی و نحوه ارتباط آن‌ها تنها با بررسی پیاده‌سازی مشخص می‌شود.

### ۵.۵. خروجی گرفتن از داده‌ها

```python
from .exporter import export_json
from .csv_exporter import export_csv
```

این importها دو نام را وارد می‌کنند:

<div align='right' dir='rtl'>

<span dir='rtl'>• `export_json`</span> <br>
<span dir='rtl'>• `export_csv`</span>

</div>

نام‌ها به قابلیت‌های مرتبط با خروجی JSON و CSV اشاره دارند. نحوه ذخیره‌سازی، قالب دقیق داده‌ها و مدیریت خطاهای فایل در ماژول‌های مربوطه تعیین می‌شود.

### ۵.۶. راه‌اندازی Logging

```python
from .logger import setup_logger
```

نام `setup_logger` از ماژول `logger` وارد می‌شود.

این نام به تنظیم یا راه‌اندازی Logging اشاره دارد. تنظیمات واقعی، مقصد پیام‌ها و اثرات احتمالی اجرای این تابع در ماژول `logger.py` مشخص می‌شوند.

## ۶. آیا Import کردن یک ماژول باعث اجرای کد آن می‌شود؟

بله. هنگام import شدن یک ماژول برای اولین بار، دستورات سطح بالای آن اجرا می‌شوند. این موضوع فقط به توابعی که بعداً فراخوانی می‌شوند محدود نیست.

برای مثال، اگر یک ماژول هنگام import شدن فایلی ایجاد کند یا تنظیمات سراسری برنامه را تغییر دهد، ممکن است این اثرات جانبی در زمان import رخ دهند.

به همین دلیل، در طراحی پکیج‌های قابل استفاده مجدد بهتر است از اجرای عملیات غیرضروری هنگام import اجتناب شود.

برای نمونه، دریافت یک درخواست شبکه یا ایجاد فایل نباید بدون دلیل صرفاً به‌خاطر import شدن یک ماژول انجام شود.

در پروژه‌های چندماژوله، این اصل به قابل پیش‌بینی بودن رفتار برنامه و ساده‌تر شدن تست‌ها کمک می‌کند.

## ۷. آیا <span dir='ltr'>`__init__.py`</span> رابط عمومی پکیج را تعریف می‌کند؟

فایل <span dir='ltr'>`__init__.py`</span> می‌تواند به ساده‌تر شدن رابط عمومی یک پکیج کمک کند.

فرض کنیم پکیجی به نام `dns_package` دارای تابع `lookup_record` در ماژول داخلی `resolver` باشد و این نام در فایل <span dir='ltr'>`__init__.py`</span> نیز وارد شده باشد.

در چنین ساختاری، ممکن است بتوان نام را از مسیر پکیج وارد کرد:

```python
from dns_package import lookup_record
```

در مقابل، بدون وارد کردن این نام در فضای نام پکیج، ممکن است لازم باشد از مسیر ماژول استفاده شود:

```python
from dns_package.resolver import lookup_record
```

این مثال فرضی است و نام `dns_package` صرفاً برای توضیح مفهوم استفاده شده است؛ مسیر import واقعی به نام پکیج و ساختار اجرای پروژه بستگی دارد.

نکته مهم این است که **قابل import بودن یک نام لزوماً به معنی تضمین یا پشتیبانی رسمی آن به‌عنوان API عمومی نیست**. طراحی API عمومی شامل تصمیم‌گیری درباره نام‌های پایدار، قرارداد استفاده و سازگاری نسخه‌های آینده نیز می‌شود.

در صورت نیاز می‌توان از متغیر `__all__` برای مشخص کردن نام‌هایی استفاده کرد که در عملیات‌هایی مانند <span dir='ltr'>`from package import *`</span> در نظر گرفته می‌شوند. بااین‌حال، استفاده از `__all__` برای همه پکیج‌ها اجباری نیست.

## ۸. نکات مهم درباره طراحی <span dir='ltr'>`__init__.py`</span>

هنگام طراحی این فایل، چند نکته را باید در نظر گرفت:

<p dir='rtl'>
• فقط نام‌هایی را وارد کنید که واقعاً به دسترسی ساده‌تر نیاز دارند. <br>
• از ایجاد وابستگی‌های حلقوی میان ماژول‌ها اجتناب کنید. <br>
• به اثرات جانبی import توجه داشته باشید. <br>
• از سنگین کردن غیرضروری فرایند import خودداری کنید. <br>
• رابط عمومی پکیج را آگاهانه طراحی کنید. <br>
• بین import کردن یک نام و فراخوانی تابع آن تفاوت قائل شوید.
</p>

برای مثال، این دستور:

```python
from .logger import setup_logger
```

نام تابع را وارد می‌کند؛ اما به‌خودی‌خود به معنی فراخوانی <span dir='ltr'>`setup_logger()`</span> نیست.

فراخوانی تابع تنها زمانی رخ می‌دهد که دستور اجرای آن نوشته شود یا در بخشی از کد به‌طور دیگری فراخوانی شود.

## ۹. خطاهای متداول

### خطای اول: اشتباه گرفتن Module و Package

ماژول معمولاً یک فایل Python است، اما پکیج برای سازمان‌دهی ماژول‌ها به کار می‌رود.

### خطای دوم: تصور اینکه Import نسبی در هر شرایطی اجرا می‌شود

<p dir='rtl'>
Import نسبی به زمینه پکیج وابسته است و اجرای مستقیم یک فایل ممکن است این زمینه را فراهم نکند.
</p>

### خطای سوم: تصور اینکه Import کردن یک تابع آن را اجرا می‌کند

<p dir='rtl'>
Import کردن یک نام و فراخوانی تابع دو عملیات متفاوت‌اند.
</p>

### خطای چهارم: وارد کردن همه اعضای داخلی بدون طراحی

وارد کردن نام‌های متعدد می‌تواند رابط پکیج را بزرگ‌تر و وابستگی‌های آن را پیچیده‌تر کند. بهتر است فقط نام‌هایی در دسترس قرار بگیرند که واقعاً برای استفاده از پکیج لازم‌اند.

### خطای پنجم: نادیده گرفتن اثرات جانبی Import

<p dir='rtl'>
Import کردن یک ماژول می‌تواند کد سطح بالای آن را اجرا کند؛ بنابراین باید از وابستگی‌های غیرضروری و عملیات پرهزینه هنگام import آگاه بود.
</p>
