# فصل چهارم: تحلیل کد پروژه DNS Lookup

## درس ۳: اجرای درخواست DNS و مدیریت خطاها در پایتون

### ۱. هدف درس

در این درس، فایل `src/resolver.py` را بررسی می‌کنیم؛ بخشی که منطق اصلی جست‌وجوی رکوردهای DNS را اجرا می‌کند.

در پایان درس، با این مفاهیم آشنا خواهید شد:

<div align='right' dir='rtl'>

<span dir='rtl'>• استفاده از کتابخانه `dnspython` برای ارسال درخواست DNS</span> <br>
<span dir='rtl'>• تبدیل پاسخ‌ها به رشته‌های قابل استفاده در بخش‌های دیگر برنامه</span> <br>
<span dir='rtl'>• مدیریت خطاهای رایج هنگام جست‌وجوی DNS</span> <br>
<span dir='rtl'>• تعریف و زنجیره‌کردن استثناهای اختصاصی</span> <br>
<span dir='rtl'>• طراحی تابعی که نتیجه جست‌وجو را به شکل ساده و مشخص برمی‌گرداند</span>

</div>

### ۲. واردکردن وابستگی‌ها

ابتدای فایل:

```python
import dns.resolver

from .exception import DNSTimeoutError
```

خط اول، ماژول `dns.resolver` از کتابخانه `dnspython` را وارد می‌کند. این ماژول برای انجام درخواست‌های DNS و دریافت پاسخ آن‌ها استفاده می‌شود.

خط دوم، استثنای اختصاصی `DNSTimeoutError` را از ماژول داخلی پروژه وارد می‌کند. استفاده از استثنای اختصاصی به برنامه اجازه می‌دهد خطای پایان مهلت درخواست DNS را با نامی مشخص و مرتبط با منطق پروژه مدیریت کند.

این جداسازی، نقش دو بخش را روشن می‌کند:

<p dir='rtl'>
• کتابخانه خارجی، عملیات DNS را انجام می‌دهد. <br>
• پروژه، خطاهای منتخب را به شکل مناسب برای منطق خودش مدیریت می‌کند.
</p>

### ۳. تابع <span dir='ltr'>`lookup_record()`</span>

کد تابع:

```python
def lookup_record(domain: str, record_type: str) -> list[str]:
    """
    Lookup DNS records.
    """
```

این تابع دو ورودی دریافت می‌کند:

<div align='right' dir='rtl'>

<span dir='rtl'>• `domain`: نام دامنه‌ای که قرار است بررسی شود.</span> <br>
<span dir='rtl'>• `record_type`: نوع رکورد مورد درخواست، مانند `A` یا `MX`.</span>

</div>

نوع خروجی با `list[str]` مشخص شده است؛ یعنی تابع فهرستی از رشته‌ها برمی‌گرداند.

این قرارداد خروجی باعث می‌شود بخش‌های دیگر برنامه بتوانند پاسخ DNS را بدون نیاز به کار مستقیم با اشیای پاسخ کتابخانه `dnspython` دریافت کنند.

نکته: این type hint قرارداد مورد انتظار تابع را توضیح می‌دهد و به‌تنهایی نوع مقادیر را در زمان اجرا تضمین نمی‌کند.

### ۴. ارسال درخواست DNS

بخش اصلی عملیات:

```python
answers = dns.resolver.resolve(domain, record_type)
return [str(answer) for answer in answers]
```

در خط اول، تابع <span dir='ltr'>`dns.resolver.resolve()`</span> درخواست DNS را برای دامنه و نوع رکورد مشخص‌شده اجرا می‌کند.

در صورت دریافت پاسخ، متغیر `answers` مجموعه پاسخ‌های حاصل از درخواست را نگه می‌دارد.

خط دوم از **List Comprehension** استفاده می‌کند:

```python
[str(answer) for answer in answers]
```

این عبارت روی پاسخ‌ها پیمایش می‌کند و هر پاسخ را با <span dir='ltr'>`str()`</span> به رشته تبدیل می‌کند. در نهایت، فهرستی از رشته‌ها به فراخواننده برگردانده می‌شود.

برای مثال، یک پاسخ فرضی برای رکورد `A` ممکن است به شکل رشته‌ای مانند `192.0.2.10` نمایش داده شود. این صرفاً نمونه‌ای از قالب پاسخ است؛ نتیجه واقعی به دامنه و پاسخ DNS بستگی دارد.

این روش، خروجی تابع را ساده و یکدست می‌کند و جزئیات اشیای داخلی کتابخانه را از مصرف‌کنندگان این تابع دور نگه می‌دارد.

### ۵. مدیریت پایان مهلت درخواست

بخش بعدی:

```python
except dns.resolver.LifetimeTimeout as exc:
    raise DNSTimeoutError('DNS query timed out') from exc
```

گاهی درخواست DNS در مهلت زمانی تعیین‌شده به نتیجه نمی‌رسد. کتابخانه `dnspython` در این وضعیت می‌تواند استثنای `LifetimeTimeout` ایجاد کند.

این کد، خطای کتابخانه را دریافت می‌کند و یک استثنای اختصاصی به نام `DNSTimeoutError` ایجاد می‌کند.

عبارت زیر اهمیت ویژه‌ای دارد:

```python
raise DNSTimeoutError('DNS query timed out') from exc
```

استفاده از `from exc` باعث می‌شود استثنای اصلی به‌عنوان علت استثنای جدید حفظ شود. این قابلیت در پایتون **Exception Chaining** نام دارد.

در نتیجه، برنامه می‌تواند خطای اختصاصی پروژه را دریافت کند و در عین حال، اطلاعات مربوط به علت اولیه خطا نیز برای بررسی فنی حفظ شود.

این طراحی یک مزیت مهم دارد: بخش‌های دیگر برنامه می‌توانند به‌جای وابستگی مستقیم به نام خطای کتابخانه خارجی، خطایی معنادار در سطح خود پروژه را مدیریت کنند.

### ۶. مدیریت پاسخ‌های ناموفق یا خالی

بخش آخر:

```python
except (
    dns.resolver.NXDOMAIN,
    dns.resolver.NoAnswer,
    dns.resolver.NoNameservers,
):
    return []
```

در این بخش، سه وضعیت مدیریت می‌شوند:

<div align='center' dir='rtl'>

| استثنا | مفهوم |
|---|---|
| `NXDOMAIN` |<span dir='rtl'> نام دامنه در DNS وجود ندارد.</span> |
| `NoAnswer` |<span dir='rtl'> برای درخواست انجام‌شده، پاسخ رکورد موردنظر در دسترس نیست.</span> |
| `NoNameservers` |<span dir='rtl'> سرورهای نام مورد استفاده نتوانسته‌اند پاسخ قابل استفاده‌ای برای درخواست فراهم کنند.</span> |

</div>

در این پیاده‌سازی، هر سه وضعیت به یک نتیجه تبدیل می‌شوند: فهرست خالی.

```python
return []
```

این تصمیم، قرارداد خروجی تابع را ساده نگه می‌دارد؛ فراخواننده در این موارد به‌جای دریافت استثنا، یک فهرست خالی دریافت می‌کند.

با این حال، سه وضعیت از نظر معنایی یکسان نیستند. اگر بخش دیگری از برنامه نیاز داشته باشد بین «دامنه وجود ندارد» و «سرور نام پاسخ مناسبی نداد» تفاوت بگذارد، باید این اطلاعات از طریق طراحی مناسب در اختیار آن بخش قرار بگیرد.

نکته مهم این است که کد فعلی دقیقاً همین سه استثنا را به فهرست خالی تبدیل می‌کند. از این موضوع نباید نتیجه گرفت که تمام خطاهای ممکن DNS در همین بخش مدیریت می‌شوند.

### ۷. مسیر اجرای تابع

رفتار کلی <span dir='ltr'>`lookup_record()`</span> را می‌توان به این شکل خلاصه کرد:

<div align='right' dir='rtl'>

<span dir='rtl'>1. دامنه و نوع رکورد به تابع داده می‌شوند.</span> <br>
<span dir='rtl'>2. تابع درخواست DNS را اجرا می‌کند.</span> <br>
<span dir='rtl'>3. اگر پاسخ دریافت شود، پاسخ‌ها به رشته تبدیل و به شکل فهرست برگردانده می‌شوند.</span> <br>
<span dir='rtl'>4. اگر درخواست با `LifetimeTimeout` مواجه شود، خطای اختصاصی `DNSTimeoutError` ایجاد می‌شود.</span> <br>
<span dir='rtl'>5. اگر یکی از سه استثنای `NXDOMAIN`، `NoAnswer` یا `NoNameservers` رخ دهد، فهرست خالی برگردانده می‌شود.</span>

</div>

بنابراین، رفتار تابع در حالت‌های مختلف مشخص است و بخش‌های دیگر برنامه می‌توانند بر اساس این قرارداد با نتیجه جست‌وجو تعامل کنند.

### ۸. ارتباط `resolver.py` با `validator.py`

در درس قبلی، تابع‌های اعتبارسنجی دامنه و نوع رکورد را بررسی کردیم. در این فایل، <span dir='ltr'>`lookup_record()`</span> مستقیماً درخواست DNS را اجرا می‌کند.

نکته معماری این است که در کد فعلی `resolver.py`، تابع‌های <span dir='ltr'>`validate_domain()`</span> و <span dir='ltr'>`validate_record_type()`</span> فراخوانی نشده‌اند. بنابراین، نباید فرض کرد که این فایل به‌تنهایی ورودی‌ها را با همان قواعد اعتبارسنجی می‌کند.

این جداسازی می‌تواند مفید باشد: اعتبارسنجی ورودی‌ها و اجرای درخواست DNS دو مسئولیت متفاوت‌اند. برای شناخت مسیر کامل اجرای برنامه، لازم است فایل‌های فراخواننده این تابع نیز بررسی شوند.

### ۹. تمرین‌های آموزشی

**تمرین اول — تبدیل پاسخ‌ها**

عبارت زیر را بررسی کنید و توضیح دهید چرا از <span dir='ltr'>`str()`</span> استفاده شده است:

```python
[str(answer) for answer in answers]
```

سپس آن را با یک حلقه `for` معمولی بازنویسی کنید.

**تمرین دوم — زنجیره‌کردن استثناها**

توضیح دهید تفاوت این دو دستور چیست:

```python
raise DNSTimeoutError("DNS query timed out")
```

```python
raise DNSTimeoutError("DNS query timed out") from exc
```

**تمرین سوم — قرارداد خروجی**

چرا برگرداندن `[]` برای بعضی پاسخ‌های ناموفق می‌تواند استفاده از تابع را ساده‌تر کند؟ در چه شرایطی حفظ تفاوت بین خطاهای مختلف اهمیت دارد؟

**تمرین چهارم — بررسی مسیر فراخوانی**

با بررسی فایل‌های دیگر پروژه مشخص کنید چه بخشی از برنامه <span dir='ltr'>`lookup_record()`</span> را فراخوانی می‌کند و آیا پیش از آن، اعتبارسنجی ورودی انجام می‌شود یا خیر.

فایل `resolver.py` هسته اجرای درخواست DNS در این بخش از پروژه است. طراحی آن چند نکته مهم دارد:

<div align='right' dir='rtl'>

<span dir='rtl'>• استفاده از `dnspython` برای انجام درخواست DNS</span> <br>
<span dir='rtl'>• ارائه پاسخ‌ها به شکل `list[str]`</span> <br>
