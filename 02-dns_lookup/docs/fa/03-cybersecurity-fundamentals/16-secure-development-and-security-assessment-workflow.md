## ۱. مقدمه

تا اینجا با مفاهیم پایه امنیت سایبری، شبکه، آسیب‌پذیری‌ها، رمزنگاری، مدیریت اطلاعات محرمانه، Logging و پایش امنیتی آشنا شدیم.

حالا باید این مفاهیم را به یک روش عملی برای توسعه ابزارهای Python تبدیل کنیم.

فرض کن می‌خواهیم ابزاری مانند DNS Lookup یا Port Scanner بسازیم. صرفاً اینکه برنامه اجرا شود و خروجی درستی بدهد کافی نیست. باید بررسی کنیم:

<p dir='rtl'>
• آیا ورودی‌های نامعتبر را به‌درستی مدیریت می‌کند؟ <br>
• آیا هنگام بروز خطا رفتار قابل پیش‌بینی دارد؟ <br>
• آیا اطلاعات حساس را افشا می‌کند؟ <br>
• آیا وابستگی‌های آن امن و به‌روز هستند؟ <br>
• آیا تست‌ها رفتار مورد انتظار را بررسی می‌کنند؟ <br>
• آیا می‌توانیم عملکرد و محدودیت‌های آن را توضیح دهیم؟
</p>

این پرسش‌ها بخشی از توسعه امن نرم‌افزار هستند.

## ۲. توسعه امن چیست؟

<div align='right' dir='rtl'>

<span dir='rtl'>**Secure Development** یعنی در تمام مراحل توسعه، امنیت را به‌عنوان یکی از نیازمندی‌های نرم‌افزار در نظر بگیریم.</span>

</div>

امنیت نباید فقط در پایان پروژه بررسی شود.

برای مثال، اگر هنگام طراحی ابزار تصمیم بگیریم تمام Exceptionها را بدون توجه به نوعشان بگیریم و فقط یک پیام عمومی نمایش دهیم، ممکن است مشکلاتی در عیب‌یابی یا مدیریت خطا ایجاد شود.

اگر از ابتدا برای خطاهای قابل انتظار و غیرمنتظره رفتار مشخصی طراحی کنیم، نتیجه معمولاً قابل پیش‌بینی‌تر و نگهداری آن آسان‌تر خواهد بود.

### مراحل کلی توسعه امن

<div align='right' dir='rtl'>

<span dir='rtl'>۱. **Design:** مشخص کردن هدف، نیازمندی‌ها و محدودیت‌ها </span> <br> 
<span dir='rtl'>۲. **Implementation:** نوشتن کد با رعایت اصول امنیتی  </span> <br>
<span dir='rtl'>۳. **Testing:** بررسی رفتار عادی، خطاها و ورودی‌های نامعتبر </span> <br> 
<span dir='rtl'>۴. **Dependency Review:** بررسی کتابخانه‌ها و وابستگی‌ها  </span> <br>
<span dir='rtl'>۵. **Security Assessment:** بررسی ریسک‌ها و ضعف‌های احتمالی  </span> <br>
<span dir='rtl'>۶. **Remediation:** اصلاح مشکلات شناسایی‌شده  </span> <br>
<span dir='rtl'>۷. **Retesting:** بررسی مجدد پس از اصلاح  </span> <br>
<span dir='rtl'>۸. **Maintenance:** نگهداری و به‌روزرسانی مستمر</span>

</div>

این مراحل همیشه کاملاً خطی نیستند. ممکن است در زمان تست یا نگهداری، به مرحله طراحی یا پیاده‌سازی برگردیم.

## ۳. اعتبارسنجی ورودی‌ها

ورودی کاربر باید قبل از استفاده بررسی شود.

برای نمونه، ابزار DNS Lookup ممکن است نام دامنه و نوع رکورد را از کاربر دریافت کند.

در این حالت باید مشخص کنیم:

<p dir='rtl'>
• آیا ورودی خالی است؟ <br>
• آیا نوع رکورد درخواستی پشتیبانی می‌شود؟ <br>
• آیا ورودی با محدودیت‌های تعریف‌شده برای برنامه سازگار است؟ <br>
• اگر ورودی نامعتبر باشد، برنامه چگونه پاسخ می‌دهد؟
</p>

مثلاً اگر ابزار فقط رکوردهای مشخصی را پشتیبانی می‌کند، باید رفتار آن برای نوع رکورد ناشناخته روشن باشد.

نکته مهم این است که اعتبارسنجی ورودی با اطمینان از معتبر بودن نتیجه یکسان نیست. حتی یک نام دامنه معتبر نیز ممکن است وجود نداشته باشد یا سرور DNS نتواند به آن پاسخ دهد.

**اصل کلیدی:** ورودی را بررسی کن، اما فرض نکن که اعتبارسنجی ورودی موفقیت عملیات را تضمین می‌کند.

## ۴. مدیریت خطا و Exceptionها

برنامه امن باید خطاها را به شکلی قابل پیش‌بینی مدیریت کند.

برای مثال، یک ابزار شبکه ممکن است با این شرایط روبه‌رو شود:

<p dir='rtl'>
• ورودی نامعتبر <br>
• Timeout <br>
• پاسخ خالی <br>
• خطای Resolver <br>
• مشکل دسترسی به شبکه <br>
• خطای غیرمنتظره در کد
</p>

این شرایط الزاماً معنای یکسانی ندارند.

### اصول مناسب مدیریت خطا

<p dir='rtl'>
• خطاهای مورد انتظار را تا حد امکان به‌صورت مشخص مدیریت کن. <br>
• پیام خطا برای کاربر واضح و متناسب باشد. <br>
• جزئیات فنی لازم برای عیب‌یابی در مقصد مناسب ثبت شوند. <br>
• اطلاعات محرمانه در پیام یا Log قرار نگیرند. <br>
• خطاهای غیرمنتظره را بی‌صدا نادیده نگیر. <br>
• رفتار برنامه هنگام شکست عملیات مشخص باشد.
</p>

برای مثال، نمایش پیام «پاسخی برای این درخواست دریافت نشد» ممکن است برای کاربر مناسب باشد؛ اما در گزارش داخلی، در صورت نیاز می‌توان نوع دقیق‌تر خطا را ثبت کرد.

البته پیام کاربر باید با واقعیت هماهنگ باشد. Timeout الزاماً به این معنی نیست که دامنه وجود ندارد.

## ۵. مدیریت وابستگی‌های Python

بسیاری از پروژه‌های Python به کتابخانه‌های خارجی وابسته‌اند.

این کتابخانه‌ها می‌توانند آسیب‌پذیری داشته باشند یا در نسخه‌های جدید اصلاحات امنیتی دریافت کنند.

بنابراین، بررسی وابستگی‌ها بخشی از نگهداری امن پروژه است.

### ۵.۱. محیط مجازی

برای جداسازی وابستگی‌های پروژه می‌توان از محیط مجازی استفاده کرد:

```bash
python -m venv .venv
```

فعال‌سازی در Linux و macOS:

```bash
source .venv/bin/activate
```

فعال‌سازی در Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

محیط مجازی به مدیریت جداگانه وابستگی‌ها کمک می‌کند، اما به‌تنهایی آسیب‌پذیری‌های آن‌ها را برطرف نمی‌کند.

### ۵.۲. مشاهده وابستگی‌ها

می‌توان بسته‌های نصب‌شده را با این دستور مشاهده کرد:

```bash
python -m pip list
```

برای بررسی سازگاری برخی وابستگی‌ها نیز می‌توان از دستور زیر استفاده کرد:

```bash
python -m pip check
```

این دستور ناسازگاری‌های اعلام‌شده میان وابستگی‌های نصب‌شده را بررسی می‌کند؛ اما **ابزار شناسایی آسیب‌پذیری امنیتی نیست**.

### ۵.۳. بررسی آسیب‌پذیری‌های شناخته‌شده

ابزاری مانند `pip-audit` می‌تواند وابستگی‌های Python را از نظر آسیب‌پذیری‌های شناخته‌شده بررسی کند.

پس از نصب آن در محیط مناسب، می‌توان اجرا کرد:

```bash
python -m pip_audit
```

وجود یک هشدار به این معنی نیست که آسیب‌پذیری حتماً در شرایط پروژه قابل بهره‌برداری است. همچنین نبود هشدار، امن بودن کامل پروژه را تضمین نمی‌کند.

هنگام بررسی نتایج باید مواردی مانند نسخه آسیب‌پذیر، نسخه اصلاح‌شده، میزان استفاده از بخش آسیب‌پذیر و امکان ارتقا را در نظر گرفت.

## ۶. تست نرم‌افزار از دیدگاه امنیت

تست فقط برای اطمینان از عملکرد صحیح در شرایط عادی نیست؛ باید رفتار برنامه در شرایط غیرعادی را هم بررسی کند.

### ۶.۱. تست مسیر موفق

بررسی می‌کنیم که عملیات با ورودی معتبر به نتیجه مورد انتظار برسد.

### ۶.۲. تست ورودی نامعتبر

بررسی می‌کنیم که ورودی نامعتبر باعث رفتار کنترل‌نشده یا پیام نامناسب نشود.

### ۶.۳. تست خطاهای عملیاتی

بررسی می‌کنیم که برنامه بتواند شرایطی مانند Timeout یا خطای وابستگی را به شکل مورد انتظار مدیریت کند.

### ۶.۴. تست مرزها

مقادیر خالی، بسیار بزرگ یا خارج از محدوده مجاز می‌توانند رفتار متفاوتی ایجاد کنند.

### ۶.۵. تست عدم افشای اطلاعات

بررسی می‌کنیم که پیام‌های خطا، Logها و خروجی برنامه حاوی رمز عبور، Token یا اطلاعات حساس غیرضروری نباشند.

### ۶.۶. تست تکرارپذیر

تست خوب باید تا حد امکان قابل تکرار باشد.

برای مثال، اگر تستی به شبکه واقعی وابسته باشد، ممکن است به دلیل شرایط شبکه نتیجه متفاوتی بدهد. برای آزمودن منطق داخلی برنامه، می‌توان در صورت مناسب بودن از Mock استفاده کرد تا رفتار وابستگی خارجی کنترل شود.

البته Mock جای تست یکپارچه با سرویس واقعی را به‌طور کامل نمی‌گیرد؛ هرکدام هدف متفاوتی دارند.

## ۷. اسکن امنیتی با ارزیابی امنیتی یکسان نیست

ابزارهای امنیتی می‌توانند اطلاعات مهمی جمع‌آوری کنند، اما خروجی آن‌ها باید تفسیر شود.

برای مثال:

<p dir='rtl'>
• Port Scanner می‌تواند وضعیت دسترسی به پورت‌های مشخص را بررسی کند. <br>
• DNS Lookup می‌تواند اطلاعات مربوط به رکوردهای DNS را دریافت کند. <br>
• ابزار بررسی وابستگی‌ها می‌تواند برخی آسیب‌پذیری‌های شناخته‌شده را گزارش کند.
</p>

هیچ‌کدام از این ابزارها به‌تنهایی امنیت کامل یک سیستم را تعیین نمی‌کنند.

### چرا؟

چون هر ابزار محدوده مشخصی دارد.

<p dir='rtl'>
Port Scanner به‌تنهایی ثابت نمی‌کند که یک سرویس آسیب‌پذیر است. باز بودن پورت ممکن است برای عملکرد عادی سیستم لازم باشد.
</p>

<p dir='rtl'>
DNS Lookup نیز با مشاهده یک رکورد نمی‌تواند به‌تنهایی درباره امنیت کامل دامنه یا سرور نتیجه‌گیری کند.
</p>

به همین ترتیب، ابزار بررسی وابستگی‌ها ممکن است مشکلاتی را گزارش کند که در شرایط مشخص پروژه قابل بهره‌برداری نیستند؛ یا نتواند ضعف‌هایی را تشخیص دهد که در محدوده بررسی آن قرار ندارند.

**خروجی ابزار، نقطه شروع بررسی است؛ نه حکم نهایی امنیت سیستم.**

## ۸. گردش‌کار ساده ارزیابی امنیت

برای بررسی یک ابزار یا سیستم، می‌توان از گردش‌کار زیر استفاده کرد.

### مرحله اول: تعیین محدوده

مشخص کن چه چیزی را بررسی می‌کنی و چه مجوزی برای انجام بررسی داری.

برای نمونه، در یک پروژه محلی، محدوده می‌تواند خود برنامه و وابستگی‌های آن باشد.

در ارزیابی شبکه، باید محدوده مجاز و محدودیت‌های عملیاتی روشن باشند.

### مرحله دوم: شناسایی دارایی‌ها

مشخص کن چه چیزهایی نیازمند محافظت هستند:

<p dir='rtl'>
• کد منبع <br>
• اطلاعات محرمانه <br>
• وابستگی‌ها <br>
• فایل‌های پیکربندی <br>
• ارتباطات شبکه <br>
• داده‌های کاربران
</p>

### مرحله سوم: شناسایی ریسک‌ها

بپرس چه چیزی ممکن است اشتباه پیش برود.

برای مثال:

<p dir='rtl'>
• ورودی نامعتبر باعث شکست کنترل‌نشده شود. <br>
• خطا اطلاعات داخلی را افشا کند. <br>
• وابستگی دارای آسیب‌پذیری باشد. <br>
• اطلاعات محرمانه وارد Git یا Log شود. <br>
• برنامه بدون محدودیت مناسب، درخواست‌های بیش‌ازحد ارسال کند.
</p>

### مرحله چهارم: اجرای بررسی‌ها

با توجه به محدوده پروژه از روش‌های مناسب استفاده کن:

<p dir='rtl'>
• تست‌های خودکار <br>
• بازبینی کد <br>
• بررسی وابستگی‌ها <br>
• بررسی تنظیمات <br>
• بررسی Logها <br>
• آزمایش کنترل‌شده رفتار برنامه
</p>

### مرحله پنجم: اولویت‌بندی یافته‌ها

هر مشکل را براساس شدت، احتمال وقوع، اثر احتمالی و شرایط بهره‌برداری بررسی کن.

تمام مشکلات اهمیت یکسانی ندارند. برای مثال، افشای یک Token معتبر ممکن است از یک پیام خطای نامناسب اهمیت بیشتری داشته باشد.

### مرحله ششم: اصلاح و تست مجدد

پس از اصلاح مشکل، دوباره بررسی کن که:

<p dir='rtl'>
• مشکل اصلی برطرف شده باشد. <br>
• اصلاح باعث ایجاد خطای جدید نشده باشد. <br>
• تست مرتبط همچنان موفق باشد. <br>
• رفتار مورد انتظار برنامه حفظ شده باشد.
</p>

### مرحله هفتم: مستندسازی

نتیجه را ثبت کن:

<p dir='rtl'>
• چه چیزی بررسی شد؟ <br>
• چه مشکلی پیدا شد؟ <br>
• چه شواهدی وجود داشت؟ <br>
• چه اقدامی انجام شد؟ <br>
• چه محدودیت‌هایی باقی مانده‌اند؟
</p>

مستندسازی دقیق باعث می‌شود ارزیابی قابل پیگیری و تکرار باشد.

## ۱۰. ارتباط این درس با پروژه‌های ما

هدف ما صرفاً یادگیری اصطلاحات امنیتی نیست. قرار است از این مفاهیم برای درک بهتر ابزارهای Python استفاده کنیم.

در پروژه Port Scanner، بررسی امنیتی می‌تواند روی موارد زیر متمرکز شود:

<p dir='rtl'>
• مدیریت Timeout و خطاهای شبکه <br>
• محدودیت‌های اسکن <br>
• تفسیر صحیح وضعیت پورت <br>
• محدود کردن محدوده بررسی به اهداف مجاز <br>
• تست رفتار ابزار در شرایط مختلف
</p>

در پروژه DNS Lookup، موضوعات مرتبط عبارت‌اند از:

<p dir='rtl'>
• اعتبارسنجی ورودی‌ها <br>
• ارسال درخواست DNS و پردازش پاسخ <br>
• مدیریت خطاهای Resolver <br>
• تفاوت پاسخ خالی با خطای عملیاتی <br>
• ثبت مناسب رویدادها <br>
• تست منطق برنامه و وابستگی به DNS
</p>

در پروژه‌های آینده، بسته به نوع ابزار، موضوعات دیگری مانند امنیت HTTP، اعتبارسنجی داده‌های وب، تحلیل Log یا مدیریت نشست‌ها اهمیت بیشتری پیدا خواهند کرد.

**قرار نیست همه موضوعات امنیتی را پیش از شروع هر پروژه به‌طور کامل یاد بگیریم. بهتر است مفاهیم مرتبط با هر ابزار را هم‌زمان با ساخت و تحلیل همان ابزار عمیق‌تر بررسی کنیم.**

## ۱۱. تمرین پایانی

برای یک ابزار Python دلخواه، یک ارزیابی اولیه انجام بده.

به این پرسش‌ها پاسخ بده:

۱. هدف ابزار چیست و محدوده استفاده مجاز آن کجاست؟

۲. چه ورودی‌هایی دریافت می‌کند؟

۳. چه خطاهایی ممکن است رخ دهند؟

۴. چه اطلاعاتی نباید در خروجی یا Log ثبت شوند؟

۵. چه وابستگی‌هایی دارد و چگونه می‌توان آن‌ها را بررسی کرد؟

۶. کدام تست‌ها برای بررسی رفتار غیرعادی لازم‌اند؟

۷. مهم‌ترین سه ریسک احتمالی چیست؟

۸. اگر مشکلی پیدا شود، چگونه اصلاح آن را تأیید می‌کنی؟

پاسخ‌ها لازم نیست پیچیده باشند. هدف این است که هنگام ساخت ابزار، امنیت را بخشی از فرایند مهندسی نرم‌افزار در نظر بگیری.

## ۱۲. جمع‌بندی فصل

در این فصل با اصول مهمی آشنا شدیم:

<p dir='rtl'>
• شناخت تهدیدها، آسیب‌پذیری‌ها و ریسک‌ها <br>
• درک سطح حمله و اصول شناسایی <br>
• شناخت کنترل‌های امنیتی و دفاع چندلایه <br>
• آشنایی با احراز هویت و مجوزدهی <br>
• درک مفاهیم پایه رمزنگاری و مدیریت اطلاعات محرمانه <br>
• شناخت اصول امنیت شبکه <br>
• آشنایی با حملات متداول شبکه <br>
• درک مدیریت آسیب‌پذیری‌ها <br>
• شناخت Logging و پایش امنیتی <br>
• آشنایی با توسعه امن، تست و ارزیابی امنیتی
</p>

اکنون هدف این نیست که همه این موضوعات را جداگانه و به‌صورت نظری ادامه بدهیم. در مراحل بعد، هر مفهوم را زمانی عمیق‌تر بررسی می‌کنیم که برای فهم یک ابزار یا تصمیم فنی واقعاً به آن نیاز داشته باشیم.

# پایان فصل سوم: Cybersecurity Fundamentals

## فصل بعد: تحلیل کد پروژه DNS Lookup

در فصل بعد، به‌جای ساخت یک ابزار جدید یا ادامه نظریه‌پردازی، سراغ پروژه DNS Lookup خودمان می‌رویم.

تحلیل را مرحله‌به‌مرحله پیش می‌بریم:

<p dir='rtl'>
۱. بررسی ساختار واقعی پروژه و مسئولیت فایل‌های موجود  <br> 
۲. دنبال کردن مسیر اجرای برنامه از CLI تا دریافت نتیجه   <br>
۳. بررسی نحوه استفاده از کتابخانه DNS   <br>
۴. تحلیل پردازش پاسخ‌ها و انواع رکوردها   <br>
۵. بررسی مدیریت Exceptionها و رفتار برنامه هنگام خطا   <br>
۶. بررسی Logging و محل استفاده از آن   <br>
۷. تحلیل تست‌ها، Mockها و پوشش رفتارهای مهم   <br>
۸. بررسی معماری، محدودیت‌ها و فرصت‌های بهبود  
</p>

در این فصل، مبنای تحلیل **کد واقعی پروژه** خواهد بود؛ نه فایل‌ها یا ماژول‌هایی که صرفاً ممکن است در یک طراحی پیشنهادی وجود داشته باشند.
