# درس ۱۵: پایش امنیتی و ثبت رویدادها

<div align='right' dir='rtl'>

## Security Monitoring & Logging

</div>

## ۱. مقدمه

فرض کن ابزار Python ما یک درخواست DNS ارسال می‌کند، اما پاسخ دریافت نمی‌کند. یا یک درخواست با خطا مواجه می‌شود. اگر ابزار فقط نتیجه را نمایش دهد، ممکن است برای فهمیدن علت مشکل اطلاعات کافی نداشته باشیم.

حالا تصور کن یک ابزار امنیتی به‌جای یک خطا، صدها خطای غیرمنتظره ثبت کند. بدون اطلاعات مناسب، تشخیص اینکه مشکل از شبکه، تنظیمات، ورودی کاربر یا خود برنامه است دشوار می‌شود.

اینجاست که دو مفهوم مهم مطرح می‌شوند:

<div align='right' dir='rtl'>

<span dir='rtl'>• **Logging:** ثبت اطلاعات مربوط به اجرای برنامه و اتفاقات آن.</span> <br>
<span dir='rtl'>• **Security Monitoring:** بررسی رویدادها برای شناسایی رفتارهای غیرعادی یا تهدیدهای امنیتی.</span>

</div>

هدف این درس، یادگیری اصول ثبت رویدادها در Python و درک نقش آن‌ها در ابزارهای امنیتی است.

---

## ۲. تفاوت Event، Log و Alert

این سه مفهوم به یکدیگر مرتبط‌اند، اما یکسان نیستند.

<div align='right' dir='rtl'>

### <span dir='rtl'>Log — گزارش ثبت‌شده</span>

</div>

<p dir='rtl'>
Log رکوردی از اتفاقی است که برنامه ثبت کرده است.
</p>

مثلاً:

```text
2026-10-09 10:30:00 INFO DNS lookup completed for example.com
```

این گزارش نشان می‌دهد که یک عملیات DNS با موفقیت به پایان رسیده است.

<div align='right' dir='rtl'>

### <span dir='rtl'>Event — رویداد</span>

</div>

<p dir='rtl'>
Event اتفاقی است که برای سیستم اهمیت دارد و می‌توان آن را ثبت یا بررسی کرد.
</p>

نمونه‌ها:

<p dir='rtl'>
• اجرای یک درخواست DNS <br>
• دریافت پاسخ از سرور <br>
• شکست در برقراری ارتباط <br>
• ورود ناموفق کاربر <br>
• تغییر تنظیمات امنیتی
</p>

هر Event لزوماً خطرناک نیست. برای مثال، شکست یک درخواست DNS ممکن است ناشی از یک مشکل عادی شبکه باشد.

<div align='right' dir='rtl'>

### <span dir='rtl'>Alert — هشدار</span>

</div>

<p dir='rtl'>
Alert زمانی ایجاد می‌شود که یک رویداد یا ترکیبی از رویدادها نیازمند توجه باشد.
</p>

مثلاً:

<p dir='rtl'>
• ثبت یک خطای DNS به‌تنهایی ممکن است فقط یک Log باشد. <br>
• تکرار بسیار زیاد خطاها در مدت کوتاه ممکن است یک Event قابل بررسی باشد. <br>
• عبور تعداد خطاها از یک آستانه مشخص می‌تواند باعث ایجاد Alert شود.
</p>

**نکته:** ثبت یک Log به‌خودی‌خود به معنی شناسایی یا جلوگیری از حمله نیست. برای ایجاد هشدار معمولاً به قواعد تشخیص، تحلیل رویدادها یا سامانه‌های پایش نیاز داریم.

---

## ۳. چرا Logging در امنیت اهمیت دارد؟

ثبت مناسب رویدادها چند کاربرد مهم دارد.

### ۳.۱. عیب‌یابی

وقتی برنامه خطا می‌دهد، Log می‌تواند به ما کمک کند بفهمیم:

<p dir='rtl'>
• کدام عملیات در حال اجرا بوده است؟ <br>
• خطا در چه زمانی اتفاق افتاده؟ <br>
• چه نوع خطایی رخ داده است؟ <br>
• آیا مشکل تکرارپذیر است؟
</p>

### ۳.۲. بررسی رخداد امنیتی

اگر رفتار مشکوکی مشاهده شود، گزارش‌های ثبت‌شده ممکن است به بررسی موارد زیر کمک کنند:

<p dir='rtl'>
• چه اتفاقی افتاده است؟ <br>
• چه زمانی رخ داده است؟ <br>
• کدام بخش سیستم درگیر بوده است؟ <br>
• آیا رویدادهای مرتبط دیگری هم وجود دارند؟
</p>

البته Log فقط به ما اطلاعاتی می‌دهد که واقعاً ثبت شده‌اند. اگر برنامه رویداد مهمی را ثبت نکرده باشد، ممکن است نتوانیم آن را از گزارش‌ها بازسازی کنیم.

### ۳.۳. تشخیص رفتار غیرعادی

بررسی مجموعه‌ای از Logها ممکن است الگوهایی را آشکار کند؛ برای مثال:

<p dir='rtl'>
• تعداد زیاد خطاهای احراز هویت <br>
• افزایش ناگهانی خطاهای شبکه <br>
• درخواست‌های بسیار پرتکرار <br>
• تلاش‌های مکرر برای دسترسی به منابع غیرمجاز <br>
• تغییرات غیرمنتظره در تنظیمات
</p>

یک رویداد منفرد همیشه نشانه حمله نیست. تشخیص مناسب معمولاً به زمینه، تعداد رویدادها و شرایط سیستم بستگی دارد.

---

## ۴. چه اطلاعاتی باید در Log ثبت شود؟

یک Log مفید باید اطلاعات کافی برای فهمیدن اتفاق را داشته باشد، بدون اینکه داده‌های حساس را افشا کند.

اطلاعات متداول عبارت‌اند از:

<div align='center' dir='rtl'>

| فیلد | کاربرد |
|---|---|
| Timestamp | زمان وقوع یا ثبت رویداد |
| Log Level | اهمیت یا شدت پیام |
| Logger Name | نام بخش تولیدکننده گزارش |
| Event Message | توضیح اتفاق |
| Context | اطلاعات لازم برای درک رویداد |
| Correlation ID | شناسه‌ای برای ارتباط دادن گزارش‌های یک عملیات |

</div>

برای مثال:

```text
2026-10-09 10:30:00 WARNING dns_lookup Timeout during DNS query
```

در این مثال، زمان، سطح گزارش و توضیح اتفاق مشخص‌اند.

### زمان‌بندی دقیق

در سیستم‌هایی که چند ماشین یا سرویس دارند، هماهنگ بودن ساعت‌ها اهمیت زیادی دارد. بدون آن، ممکن است ترتیب رخدادها به‌اشتباه تفسیر شود.

در سامانه‌های توزیع‌شده، استفاده از زمان استاندارد مانند UTC می‌تواند مقایسه گزارش‌ها را آسان‌تر کند.

### ثبت Context مناسب

برای ابزار DNS Lookup، بسته به نیاز و حساسیت اطلاعات، Context ممکن است شامل موارد زیر باشد:

<p dir='rtl'>
• نوع عملیات DNS <br>
• نوع رکورد درخواستی <br>
• مدت‌زمان اجرای درخواست <br>
• نتیجه کلی عملیات <br>
• نوع خطای رخ‌داده
</p>

اطلاعات باید به‌اندازه‌ای باشند که عیب‌یابی را آسان کنند، نه اینکه هر داده‌ای را بدون دلیل ثبت کنیم.

## ۵. سطوح Logging در Python

کتابخانه استاندارد `logging` در Python چند سطح اصلی دارد.

<div align='center' dir='rtl'>

| سطح | کاربرد |
|---|---|
| `DEBUG` | جزئیات زیاد برای توسعه و عیب‌یابی |
| `INFO` | اطلاع‌رسانی درباره عملیات عادی |
| `WARNING` | وضعیت غیرمنتظره‌ای که لزوماً اجرای برنامه را متوقف نمی‌کند |
| `ERROR` | خطایی که مانع انجام یک عملیات شده است |
| `CRITICAL` | خطای بسیار جدی که ممکن است عملکرد کل برنامه را تهدید کند |

</div>

برای مثال، اگر یک درخواست DNS با موفقیت انجام شود، ممکن است از `INFO` استفاده کنیم. اگر عملیات به دلیل Timeout شکست بخورد، بسته به رفتار مورد انتظار برنامه، `WARNING` یا `ERROR` می‌تواند مناسب باشد.

**انتخاب سطح گزارش باید براساس معنای واقعی اتفاق باشد، نه صرفاً نام Exception.**

یک خطای قابل انتظار در شبکه لزوماً به معنی خرابی کل برنامه نیست.

---

## ۶. آشنایی با `logging` در Python

کتابخانه `logging` به‌صورت استاندارد در Python وجود دارد و معمولاً نیازی به نصب جداگانه ندارد.

### ۶.۱. یک مثال ساده

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)

logger = logging.getLogger(__name__)

logger.debug("Detailed diagnostic information")
logger.info("DNS lookup completed")
logger.warning("DNS query timed out")
logger.error("DNS lookup failed")
```

در این مثال:

<div align='right' dir='rtl'>

<span dir='rtl'>• <span dir='ltr'>`basicConfig()`</span> تنظیمات پایه Logging را مشخص می‌کند.</span> <br>
<span dir='rtl'>• `level=logging.INFO` پیام‌های سطح INFO و سطوح مهم‌تر را نمایش می‌دهد.</span> <br>
<span dir='rtl'>• `format` قالب گزارش را تعیین می‌کند.</span> <br>
<span dir='rtl'>• `getLogger(__name__)` یک Logger با نام ماژول جاری دریافت می‌کند.</span>

</div>

از آنجا که سطح Logging روی `INFO` تنظیم شده، پیام `DEBUG` در خروجی عادی نمایش داده نمی‌شود.

### ۶.۲. چرا از `getLogger(__name__)` استفاده می‌کنیم؟

در پروژه‌ای که چند ماژول دارد، بهتر است هر ماژول Logger خودش را داشته باشد:

```python
import logging

logger = logging.getLogger(__name__)
```

این کار کمک می‌کند مشخص باشد هر پیام از کدام ماژول آمده است.

در پروژه‌های چندماژوله، معمولاً پیکربندی اصلی Logging در نقطه ورود برنامه، مانند CLI، انجام می‌شود؛ ماژول‌های قابل استفاده مجدد فقط پیام‌های موردنیاز را ثبت می‌کنند.

این جداسازی از تنظیم مکرر Logging در ماژول‌های مختلف جلوگیری می‌کند.

## ۷. ثبت Exceptionها به شکل مناسب

فرض کن اجرای یک عملیات با خطا مواجه می‌شود. ثبت نوع خطا می‌تواند برای عیب‌یابی مفید باشد.

```python
import logging

logger = logging.getLogger(__name__)

try:
    result = perform_operation()
except RuntimeError:
    logger.exception("Operation failed")
```

در این مثال، <span dir='ltr'>`logger.exception()`</span> پیام را همراه با اطلاعات Exception و Traceback ثبت می‌کند.

این متد معمولاً باید داخل بلوک `except` استفاده شود.

<p dir='rtl'>
Traceback می‌تواند برای پیدا کردن محل خطا بسیار مفید باشد، اما ممکن است اطلاعات داخلی برنامه را هم آشکار کند. بنابراین باید مقصد و دسترسی به گزارش‌ها را کنترل کنیم.
</p>

### آیا باید همه خطاها را بگیریم؟

خیر.

گرفتن Exceptionهای بیش‌ازحد عمومی و ادامه دادن اجرای برنامه بدون مدیریت درست خطا می‌تواند مشکلات را پنهان کند.

بهتر است:

<p dir='rtl'>
1. خطاهای مورد انتظار را مشخص کنیم. <br>
2. آن‌ها را در سطح مناسب مدیریت کنیم. <br>
3. اطلاعات مفید ثبت کنیم. <br>
4. خطاهای غیرمنتظره را به شکلی مدیریت کنیم که علت اصلی آن‌ها پنهان نشود.
</p>

## ۸. چه اطلاعاتی نباید ثبت شوند؟

یکی از مهم‌ترین اصول امنیتی Logging این است که گزارش‌ها نباید به محل نشت اطلاعات حساس تبدیل شوند.

### اطلاعاتی که معمولاً نباید در Log ثبت شوند

<p dir='rtl'>
• Password <br>
• API Key <br>
• Access Token و Refresh Token <br>
• Private Key <br>
• اطلاعات احراز هویت <br>
• محتوای حساس درخواست‌ها یا پاسخ‌ها <br>
• اطلاعات شخصی غیرضروری
</p>

برای مثال، این کار خطرناک است:

```python
logger.info("User credentials: %s", credentials)
```

اگر `credentials` شامل رمز عبور یا Token باشد، اطلاعات حساس وارد گزارش می‌شوند.

بهتر است فقط نتیجه عملیات ثبت شود:

```python
logger.info("Authentication attempt completed")
```

البته این پیام به‌تنهایی ممکن است برای عیب‌یابی کافی نباشد؛ اطلاعات تکمیلی باید براساس نیاز واقعی، سیاست حریم خصوصی و سطح دسترسی انتخاب شوند.

### اصل مهم

**هر اطلاعاتی که برای اجرای برنامه لازم است، لزوماً برای ثبت در Log لازم نیست.**

همچنین بهتر است پیش از ثبت داده‌های ورودی کاربر، کاراکترهای کنترلی و مقادیر نامطمئن بررسی یا پاک‌سازی شوند. در غیر این صورت، ورودی دست‌کاری‌شده ممکن است ظاهر گزارش‌ها را تغییر دهد یا پیام‌های جعلی به آن‌ها تزریق کند.

## ۹. تفاوت Logging با <span dir='ltr'>`print()`</span>

در برنامه‌های کوچک، استفاده از <span dir='ltr'>`print()`</span> برای نمایش نتیجه کافی است.

اما Logging امکانات بیشتری دارد:

<p dir='rtl'>
• سطوح مختلف پیام <br>
• ثبت نام Logger <br>
• زمان‌بندی خودکار <br>
• امکان ارسال گزارش به فایل یا مقصدهای دیگر <br>
• قابلیت تنظیم سطح گزارش بدون تغییر همه پیام‌ها <br>
• ادغام آسان‌تر با سامانه‌های پایش
</p>

برای مثال، در یک ابزار CLI می‌توان نتیجه‌ای را که کاربر باید ببیند از طریق خروجی معمول برنامه نمایش داد، اما جزئیات فنی اجرای عملیات را با Logging ثبت کرد.

این دو کاربرد یکسان نیستند:

<div align='right' dir='rtl'>

<span dir='rtl'>• **Output:** اطلاعاتی که کاربر برای استفاده از ابزار نیاز دارد.</span> <br>
<span dir='rtl'>• **Log:** اطلاعاتی که برای عیب‌یابی، بررسی و پایش سیستم مفیدند.</span>

</div>

نباید تمام پیام‌های داخلی برنامه را بدون دلیل به خروجی کاربر منتقل کنیم.

## ۱۰. از Log تا Security Monitoring

داشتن Log مفید است، اما Monitoring به بررسی و تحلیل این گزارش‌ها نیاز دارد.

یک فرایند ساده را در نظر بگیر:

<p dir='rtl'>
1. برنامه رویدادهای مهم را ثبت می‌کند. <br>
2. گزارش‌ها در مقصد مشخصی ذخیره می‌شوند. <br>
3. رویدادهای مرتبط بررسی می‌شوند. <br>
4. قواعد یا آستانه‌های تشخیص اجرا می‌شوند. <br>
5. در صورت نیاز، هشدار ایجاد می‌شود. <br>
6. فرد مسئول رویداد را بررسی می‌کند.
</p>

در سیستم‌های بزرگ، گزارش‌ها ممکن است به یک سامانه مرکزی ارسال شوند تا امکان جست‌وجو و تحلیل میان چند سرویس فراهم شود.

### نگهداری و محافظت از گزارش‌ها

<p dir='rtl'>
Logها هم باید محافظت شوند.
</p>

به این موارد توجه کن:

<p dir='rtl'>
• دسترسی به گزارش‌ها محدود باشد. <br>
• مدت نگهداری آن‌ها مشخص شود. <br>
• از پر شدن دیسک جلوگیری شود. <br>
• چرخش فایل‌های Log یا Log Rotation در نظر گرفته شود. <br>
• در صورت نیاز، گزارش‌ها به مقصدی جداگانه منتقل شوند. <br>
• تغییر یا حذف غیرمجاز گزارش‌ها تا حد امکان قابل شناسایی باشد.
</p>

نگهداری نامحدود گزارش‌ها همیشه تصمیم درستی نیست؛ ممکن است هزینه ایجاد کند یا اطلاعات حساس را بیش از زمان لازم حفظ کند.

## ۱۱. ارتباط Logging با پروژه DNS Lookup

در ابزار Logging، DNS Lookup می‌تواند درک رفتار برنامه را آسان‌تر کند.

برای نمونه، می‌توان این دسته از اتفاقات را در نظر گرفت:

<div align='center' dir='rtl'>

| اتفاق | اطلاعات مفید برای ثبت |
|---|---|
| آغاز یک درخواست | نوع عملیات و رکورد درخواستی |
| دریافت پاسخ | نتیجه کلی و مدت‌زمان عملیات |
| Timeout | نوع عملیات و نوع خطا |
| دامنه نامعتبر | توضیح خطای ورودی، بدون افشای اطلاعات غیرضروری |
| خطای پیش‌بینی‌نشده | پیام مناسب و اطلاعات Exception در مقصد امن |

</div>

البته همه این موارد نباید الزاماً با یک سطح Logging ثبت شوند. انتخاب سطح مناسب به رفتار واقعی برنامه بستگی دارد.

### خطای DNS همیشه رخداد امنیتی نیست

فرض کن درخواست DNS به Timeout می‌رسد. این اتفاق می‌تواند ناشی از مواردی مانند زیر باشد:

<p dir='rtl'>
• مشکل ارتباط شبکه <br>
• پاسخ ندادن Resolver <br>
• محدودیت‌های محیط اجرا <br>
• تنظیمات نادرست <br>
• اختلال موقت سرویس
</p>

بنابراین نباید هر Timeout را حمله امنیتی تلقی کنیم.

در مقابل، افزایش غیرعادی تعداد خطاها یا درخواست‌ها ممکن است ارزش بررسی داشته باشد.

**یک Log به‌تنهایی علت قطعی رخداد را مشخص نمی‌کند؛ باید آن را در زمینه مناسب تفسیر کرد.**

<div align='right' dir='rtl'>

### <span dir='rtl'>Logging در ابزارهای امنیتی</span>

</div>

در ابزارهای امنیتی، گزارش‌ها باید به دو پرسش پاسخ دهند:

<p dir='rtl'>
1. چه اتفاقی در ابزار افتاد؟ <br>
2. چه اطلاعاتی برای فهمیدن علت آن اتفاق لازم است؟
</p>

اما نباید بدون دلیل، تمام داده‌های دریافتی از شبکه یا تمام ورودی‌های کاربر را ثبت کنیم.

---

## ۱۲. چند اشتباه رایج

### اشتباه اول: ثبت تمام اطلاعات

ثبت همه ورودی‌ها و خروجی‌ها ممکن است اطلاعات حساس را افشا کند.

**راهکار:** فقط اطلاعات ضروری و متناسب با هدف گزارش را ثبت کن.

### اشتباه دوم: ثبت نکردن خطاها

اگر عملیات شکست بخورد و هیچ اطلاعاتی ثبت نشود، عیب‌یابی دشوار می‌شود.

**راهکار:** خطاهای مهم را در محل مناسب مدیریت و ثبت کن.

### اشتباه سوم: یکسان دانستن تمام خطاها

یک Timeout قابل انتظار با یک خطای برنامه‌نویسی غیرمنتظره یکسان نیست.

**راهکار:** نوع خطا و اثر آن بر عملیات را در انتخاب سطح گزارش در نظر بگیر.

### اشتباه چهارم: پیکربندی Logging در تمام ماژول‌ها

این کار می‌تواند باعث پیکربندی‌های تکراری یا رفتار نامناسب در برنامه‌های چندماژوله شود.

**راهکار:** Logger را در هر ماژول دریافت کن و پیکربندی اصلی را معمولاً در نقطه ورود برنامه انجام بده.

### اشتباه پنجم: اعتماد کامل به Logها

ممکن است بعضی رویدادها ثبت نشده باشند یا گزارش‌ها ناقص و حتی دست‌کاری‌شده باشند.

**راهکار:** Log را یک منبع شواهد بدان، نه حقیقت کامل و قطعی.

## ۱۳. تمرین‌های عملی

### تمرین اول: سطح مناسب Logging

برای هر مورد مشخص کن کدام سطح مناسب‌تر است و چرا:

<p dir='rtl'>
1. عملیات DNS با موفقیت انجام شده است. <br>
2. یک درخواست DNS به Timeout رسیده است. <br>
3. برنامه به دلیل یک خطای غیرمنتظره نتوانسته عملیات مهمی را تکمیل کند. <br>
4. توسعه‌دهنده برای عیب‌یابی به جزئیات داخلی بیشتری نیاز دارد.
</p>

پاسخ‌ها ممکن است بسته به اثر اتفاق و رفتار مورد انتظار برنامه متفاوت باشند؛ دلیل انتخاب مهم‌تر از حفظ کردن نام سطوح است.

### تمرین دوم: شناسایی اطلاعات حساس

این پیام را بررسی کن:

```python
logger.info(
    "Request failed: token=%s password=%s",
    token,
    password,
)
```

به این پرسش‌ها پاسخ بده:

<p dir='rtl'>
• چه مشکلی دارد؟ <br>
• چرا حذف رمز عبور به‌تنهایی کافی نیست؟ <br>
• چه اطلاعاتی را می‌توان به‌جای آن ثبت کرد؟
</p>

### تمرین سوم: طراحی Log برای DNS Lookup

برای یک عملیات DNS مشخص کن:

<p dir='rtl'>
• چه زمانی باید Log ثبت شود؟ <br>
• چه اطلاعاتی باید در آن باشد؟ <br>
• چه اطلاعاتی نباید ثبت شود؟ <br>
• کدام خطاها قابل انتظارند؟ <br>
• چه اتفاقی ممکن است ارزش بررسی امنیتی داشته باشد؟
</p>

### تمرین چهارم: بررسی Logger

کد زیر را بررسی کن:

```python
import logging

logger = logging.getLogger(__name__)


def run_operation() -> None:
    try:
        perform_operation()
    except RuntimeError:
        logger.exception("Operation failed")
        raise
```

به این پرسش‌ها پاسخ بده:

<div align='right' dir='rtl'>

<span dir='rtl'>• چرا از `getLogger(__name__)` استفاده شده است؟</span> <br>
<span dir='rtl'>• <span dir='ltr'>`logger.exception()`</span> چه اطلاعاتی ثبت می‌کند؟</span> <br>
<span dir='rtl'>• چرا بعد از ثبت خطا دوباره آن را با `raise` بالا می‌بریم؟</span> <br>
<span dir='rtl'>• در چه شرایطی ممکن است ثبت مجدد همین Exception در لایه بالاتر باعث تکرار غیرضروری گزارش شود؟</span>

</div>
