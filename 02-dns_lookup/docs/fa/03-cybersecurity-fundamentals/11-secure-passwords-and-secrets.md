## Secure Passwords & Secrets

## ۱. اطلاعات محرمانه (Secrets) چیست؟

در توسعه نرم‌افزار، **Secret** به اطلاعاتی گفته می‌شود که افشای آن‌ها می‌تواند امنیت یک سیستم یا حساب کاربری را به خطر بیندازد.

نمونه‌های رایج:

<p dir='rtl'>
• رمز عبور کاربران یا حساب‌های سرویس <br>
• API Key <br>
• Access Token <br>
• Refresh Token <br>
• کلید خصوصی رمزنگاری <br>
• رمز عبور پایگاه داده <br>
• کلیدهای امضای دیجیتال <br>
• اطلاعات اتصال به سرویس‌های خارجی
</p>

برای مثال، فرض کن یک برنامه Python برای اتصال به یک سرویس خارجی از API Key استفاده می‌کند. اگر این کلید در یک مخزن عمومی GitHub منتشر شود، شخص دیگری ممکن است از آن برای دسترسی غیرمجاز یا مصرف منابع استفاده کند.

**اصل مهم:** اطلاعات محرمانه نباید بدون نیاز در کد منبع، فایل‌های عمومی، Logها یا مخازن Git ذخیره شوند.

---

## ۲. تفاوت API Key، Password و Token

این اصطلاحات به هم مرتبط‌اند، اما یکسان نیستند.

<div align='center' dir='rtl'>

| نوع | کاربرد معمول | نمونه |
|---|---|---|
| Password | احراز هویت یک کاربر یا حساب | رمز عبور ورود |
| API Key | شناسایی یا مجاز کردن یک برنامه یا مصرف‌کننده API | کلید دسترسی به یک سرویس |
| Access Token | ارائه اطلاعات یا مجوز دسترسی در یک بازه یا زمینه مشخص | Token دسترسی به API |
| Refresh Token |<span dir='rtl'> دریافت Access Token جدید طبق سیاست سامانه</span> | Token تمدید دسترسی |
| Private Key | انجام عملیات رمزنگاری یا امضا با کلید خصوصی | کلید امضای دیجیتال |

</div>

نحوه دقیق استفاده از این اطلاعات به طراحی سرویس بستگی دارد. برای مثال، همه API Keyها سازوکار یکسانی ندارند و نباید فرض کنیم که هر کلید به‌تنهایی احراز هویت قوی یا مجوزهای دقیق فراهم می‌کند.

---

## ۳. چرا نباید Secretها را داخل کد قرار دهیم؟

فرض کن برنامه‌ای با این کد نوشته‌ایم:

```python
API_KEY = "my-secret-api-key"
```

این روش مشکل‌ساز است؛ زیرا ممکن است کلید به روش‌های مختلف افشا شود:

<p dir='rtl'>
• کد در GitHub عمومی منتشر شود. <br>
• فایل به شخص دیگری ارسال شود. <br>
• کلید در تاریخچه Git باقی بماند. <br>
• نسخه‌ای از کد در Backup یا سیستم دیگری ذخیره شود. <br>
• فردی که به مخزن دسترسی دارد، کلید را مشاهده کند.
</p>

حتی اگر بعداً خط حاوی کلید را حذف کنیم، ممکن است مقدار قبلی همچنان در تاریخچه Git وجود داشته باشد.

### روش بهتر

اطلاعات محرمانه را از کد جدا کن و هنگام اجرا از یک منبع مناسب دریافت کن؛ برای مثال:

<p dir='rtl'>
• متغیرهای محیطی (Environment Variables) <br>
• فایل محلی خارج از مخزن Git <br>
• Secret Manager <br>
• سامانه مدیریت کلیدها، در صورت نیاز
</p>

برای پروژه‌های کوچک آموزشی، متغیر محیطی یا فایل محلی نادیده‌گرفته‌شده توسط Git می‌تواند گزینه‌ای ساده باشد.

برای سیستم‌های سازمانی، باید مدیریت دسترسی، چرخش کلیدها، ثبت رویدادها و چرخه عمر Secretها نیز در نظر گرفته شوند.

## ۴. استفاده از Environment Variables در Python

متغیرهای محیطی به برنامه اجازه می‌دهند تنظیمات را خارج از کد دریافت کند.

<div align='right' dir='rtl'>

<span dir='rtl'>Python برای دسترسی به آن‌ها ماژول استاندارد `os` را فراهم می‌کند.</span>

</div>

### مثال

```python
import os

api_key = os.getenv("MY_API_KEY")

if not api_key:
    raise RuntimeError("MY_API_KEY is not configured")

# Use api_key with the intended service.
```

در این مثال:

<div align='right' dir='rtl'>

<span dir='rtl'>• <span dir='ltr'>`os.getenv()`</span> مقدار متغیر محیطی را می‌خواند.</span> <br>
<span dir='rtl'>• اگر متغیر وجود نداشته باشد، مقدار `None` برمی‌گردد.</span> <br>
<span dir='rtl'>• برنامه به‌جای ادامه کار با تنظیمات ناقص، خطای مشخصی ایجاد می‌کند.</span>

</div>

البته در یک برنامه واقعی باید بررسی شود که مقدار دریافت‌شده در قالب مورد انتظار است و استفاده از آن در سرویس مقصد نیز به‌درستی مدیریت می‌شود.

### تنظیم متغیر در Linux و macOS

در یک ترمینال می‌توان نوشت:

```bash
export MY_API_KEY="your-secret-value"
python app.py
```

این متغیر معمولاً برای فرایندهای اجراشده از همان محیط ترمینال در دسترس خواهد بود.

### تنظیم متغیر در PowerShell

```powershell
$env:MY_API_KEY = "your-secret-value"
python app.py
```

این مقدار معمولاً تا پایان عمر همان نشست محیطی باقی می‌ماند.

### نکته امنیتی

<p dir='rtl'>
Environment Variable به‌خودی‌خود یک Secret Manager کامل نیست. بسته به سیستم‌عامل، مجوزهای فرایندها، ابزارهای مدیریت سیستم و نحوه اجرا، ممکن است اطلاعات محیطی در معرض مشاهده قرار بگیرند.
</p>

همچنین نباید مقدار Secret را برای بررسی صحت تنظیمات چاپ کنیم.

## ۵. استفاده از فایل <span dir='ltr'>`.env`</span> در پروژه‌های Python

در پروژه‌های محلی، گاهی از فایل <span dir='ltr'>`.env`</span> برای نگهداری تنظیمات محیطی استفاده می‌شود.

مثال محتوای فایل:

```dotenv
MY_API_KEY=your-secret-value
DEBUG=false
```

فایل <span dir='ltr'>`.env`</span> می‌تواند برای محیط توسعه مناسب باشد، اما معمولاً باید از مخزن Git خارج بماند.

برای خواندن این فایل در Python می‌توان از کتابخانه‌ای مانند `python-dotenv` استفاده کرد.

نصب:

```bash
python -m pip install python-dotenv
```

استفاده:

```python
import os
from dotenv import load_dotenv

load_dotenv()

api_key = os.getenv("MY_API_KEY")

if not api_key:
    raise RuntimeError("MY_API_KEY is not configured")
```

تابع <span dir='ltr'>`load_dotenv()`</span> متغیرهای تعریف‌شده در فایل <span dir='ltr'>`.env`</span> را در محیط برنامه بارگذاری می‌کند.

### نکات مهم

<div align='right' dir='rtl'>

<span dir='rtl'>• فایل <span dir='ltr'>`.env`</span> را عمومی نکن.</span> <br>
<span dir='rtl'>• فایل <span dir='ltr'>`.env`</span> را به Git اضافه نکن.</span> <br>
<span dir='rtl'>• برای تیم، قالبی مانند <span dir='ltr'>`.env.example`</span> بساز که فقط نام تنظیمات موردنیاز را نشان دهد.</span> <br>
<span dir='rtl'>• مقدار واقعی Secret را در <span dir='ltr'>`.env.example`</span> قرار نده.</span> <br>
<span dir='rtl'>• در محیط عملیاتی، از روش مدیریت Secret متناسب با زیرساخت استفاده کن.</span>

</div>

مثال فایل <span dir='ltr'>`.env.example`</span>:

```dotenv
MY_API_KEY=
DEBUG=false
```

این فایل به توسعه‌دهنده نشان می‌دهد چه تنظیماتی لازم است، بدون اینکه اطلاعات واقعی محرمانه را افشا کند.

## ۶. جلوگیری از ثبت Secret در Git

یکی از اشتباهات رایج، قرار دادن فایل‌های حاوی اطلاعات محرمانه در مخزن Git است.

فایل <span dir='ltr'>`.gitignore`</span> برای مشخص کردن فایل‌هایی استفاده می‌شود که نباید به‌طور معمول توسط Git دنبال شوند.

برای مثال:

```gitignore
.env
.env.*
!.env.example
__pycache__/
*.py[cod]
.venv/
venv/
```

این تنظیمات فایل <span dir='ltr'>`.env`</span> و فایل‌های مشابه را نادیده می‌گیرد، اما <span dir='ltr'>`.env.example`</span> را مستثنا می‌کند.

بااین‌حال، این الگو به‌تنهایی تمام فایل‌های ممکن را پوشش نمی‌دهد؛ باید ساختار پروژه و سیاست نام‌گذاری فایل‌ها را نیز در نظر گرفت.

### نکته بسیار مهم درباره Git

<div align='right' dir='rtl'>

<span dir='rtl'><span dir='ltr'>`.gitignore`</span> فقط مانع اضافه شدن خودکار فایل‌های نادیده‌گرفته‌شده به مخزن می‌شود.</span>

</div>

اگر فایلی قبلاً Commit شده باشد، افزودن نام آن به <span dir='ltr'>`.gitignore`</span> آن را از تاریخچه Git حذف نمی‌کند.

برای بررسی وضعیت:

```bash
git status
```

برای بررسی اینکه Git یک فایل را دنبال می‌کند یا نه:

```bash
git ls-files .env
```

اگر فایل قبلاً Commit شده باشد، باید علاوه بر حذف آن از وضعیت دنبال‌شده مخزن، احتمال افشای اطلاعات را نیز بررسی کنیم.

**اگر Secret واقعی منتشر شد، فقط حذف فایل کافی نیست؛ Secret را از سرویس مربوطه باطل یا تعویض کن.**

در صورت نیاز، تاریخچه مخزن نیز باید با دقت پاک‌سازی شود؛ اما این کار جایگزین تعویض Secret افشاشده نیست.

## ۷. مدیریت امن رمز عبور کاربران

در درس قبلی یاد گرفتیم که رمز عبور را نباید به‌صورت متن ساده ذخیره کرد.

اما چرا؟

فرض کن پایگاه داده یک برنامه به سرقت برود. اگر رمزهای عبور به‌صورت متن ساده ذخیره شده باشند، مهاجم مستقیماً آن‌ها را خواهد داشت.

به همین دلیل، سامانه‌های متعارف احراز هویت باید از روش‌های تخصصی ذخیره رمز عبور استفاده کنند.

### روش‌های رایج

<p dir='rtl'>
• Argon2id <br>
• scrypt <br>
• bcrypt <br>
• PBKDF2
</p>

این روش‌ها برای مشتق‌سازی خروجی از رمز عبور طراحی شده‌اند و استفاده از تنظیمات مناسب آن‌ها هزینه حدس زدن انبوه رمزها را افزایش می‌دهد.

<div align='right' dir='rtl'>

### Salt

</div>

<p dir='rtl'>
Salt مقداری است که برای هر رمز عبور به‌صورت یکتا استفاده می‌شود.
</p>

<p dir='rtl'>
Salt کمک می‌کند رمزهای عبور یکسان الزاماً مقدار ذخیره‌شده یکسانی نداشته باشند و استفاده از جداول ازپیش‌محاسبه‌شده دشوارتر شود.
</p>

<p dir='rtl'>
Salt معمولاً محرمانه نیست و کتابخانه مناسب ذخیره رمز عبور می‌تواند آن را مدیریت کند.
</p>

### نکته

برای ذخیره رمز عبور، نباید صرفاً از این روش استفاده کنیم:

```python
import hashlib

password_hash = hashlib.sha256(
    password.encode("utf-8")
).hexdigest()
```

این کد یک Hash محاسبه می‌کند، اما روش مناسبی برای ذخیره رمز عبور کاربران نیست؛ زیرا SHA-256 سریع است و امکان آزمایش تعداد زیادی حدس را فراهم می‌کند.

برای این کاربرد باید از کتابخانه و الگوریتم تخصصی ذخیره رمز عبور استفاده کنیم.

---

## ۸. تفاوت Hash کردن رمز عبور و رمزنگاری آن

این دو روش هدف یکسانی ندارند.

### رمزنگاری رمز عبور

اگر رمز عبور را با الگوریتم رمزنگاری متقارن رمز کنیم، بازیابی آن با کلید مناسب ممکن است.

این روش برای ذخیره رمز عبور ورود کاربران، معمولاً انتخاب مناسبی نیست؛ زیرا برنامه نباید به بازیابی متن اصلی رمز عبور نیاز داشته باشد.

<div align='right' dir='rtl'>

### <span dir='rtl'>Hash تخصصی رمز عبور</span>

</div>

در روش متعارف، برنامه هنگام ثبت‌نام خروجی یک الگوریتم تخصصی را ذخیره می‌کند.

هنگام ورود، رمز عبور واردشده دوباره بررسی می‌شود تا مشخص شود با مقدار ذخیره‌شده مطابقت دارد یا خیر.

در این فرایند نیازی به بازیابی متن اصلی رمز عبور از مقدار ذخیره‌شده نیست.

**اصل مهم:** رمز عبور را برای ورود کاربران ذخیره می‌کنیم تا بتوانیم آن را بررسی کنیم، نه اینکه بعداً متن اصلی آن را بازیابی کنیم.

البته برخی سامانه‌ها ممکن است برای کاربردهای متفاوت، اطلاعات محرمانه‌ای را رمزنگاری کنند که واقعاً به بازیابی نیاز دارد. آن سناریو با ذخیره رمز عبور ورود متفاوت است.

## ۹. مدیریت Tokenها و API Keyها

<p dir='rtl'>
Tokenها و API Keyها ممکن است دسترسی مهمی به منابع فراهم کنند. بنابراین باید مانند اطلاعات محرمانه با آن‌ها رفتار کنیم.
</p>

### اصول مهم

#### ۹.۱. حداقل دسترسی

برای هر کلید فقط مجوزهای موردنیاز را فعال کن.

اگر یک ابزار فقط نیاز به خواندن اطلاعات دارد، در صورت پشتیبانی سرویس، از کلیدی با مجوز خواندن استفاده کن؛ نه کلیدی با دسترسی مدیریتی کامل.

#### ۹.۲. محدود کردن دامنه استفاده

اگر سرویس مقصد امکان محدود کردن کلید بر اساس پروژه، منبع، IP یا نوع عملیات را فراهم می‌کند، از محدودیت‌های مناسب استفاده کن.

#### ۹.۳. انقضا و چرخش

برای Tokenها و کلیدهایی که قابلیت انقضا یا چرخش دارند، سیاست مناسبی تعریف کن.

چرخش کلید باید با برنامه‌ریزی انجام شود تا سرویس‌های مجاز دچار اختلال نشوند.

#### ۹.۴. لغو کلید افشاشده

اگر یک کلید منتشر یا سرقت شد:

<p dir='rtl'>
1. کلید را در سرویس صادرکننده لغو یا غیرفعال کن. <br>
2. کلید جدیدی با مجوزهای مناسب بساز. <br>
3. محل‌های استفاده از کلید قبلی را بررسی کن. <br>
4. Logهای مربوط را برای فعالیت مشکوک بررسی کن. <br>
5. علت افشا را برطرف کن. <br>
6. مطمئن شو کلید جدید نیز به مخزن یا Logها راه پیدا نمی‌کند.
</p>

#### ۹.۵. محافظت از Tokenهای نشست

<p dir='rtl'>
Tokenهای نشست و Refresh Tokenها ممکن است امکان دسترسی به حساب کاربر را فراهم کنند.
</p>

نباید آن‌ها را در Logهای عمومی، گزارش‌های قابل مشاهده برای دیگران یا مخزن کد منتشر کرد.

---

## ۱۰. جلوگیری از افشای Secret در Logها و پیام‌های خطا

گاهی برنامه رمز عبور را مستقیماً چاپ نمی‌کند، اما اطلاعات محرمانه را در پیام خطا یا Log ثبت می‌کند.

برای مثال، این روش ناامن است:

```python
logger.info("Using API key: %s", api_key)
```

چون مقدار واقعی کلید در Log ثبت می‌شود.

روش مناسب‌تر:

```python
logger.info("API key has been configured")
```

در این حالت، فقط وضعیت پیکربندی ثبت می‌شود و مقدار Secret افشا نمی‌شود.

### مواردی که نباید بی‌دلیل Log شوند

<p dir='rtl'>
• رمز عبور <br>
• API Key <br>
• Access Token <br>
• Refresh Token <br>
• کلید خصوصی <br>
• اطلاعات حساس احراز هویت <br>
• اطلاعات شخصی غیرضروری
</p>

علاوه بر محتوای Log، باید به محل ذخیره، سطح دسترسی و مدت نگهداری آن نیز توجه کنیم.

برای پروژه‌های Python که در GitHub منتشر می‌شوند، این چک‌لیست مفید است.

### اگر مخزن عمومی است

عمومی بودن مخزن به این معنا نیست که تمام تنظیمات باید عمومی باشند.

کد برنامه معمولاً می‌تواند عمومی باشد، اما مقدار واقعی Secretها باید از کد جدا بماند.

---

## ۱۲. ارتباط این درس با پروژه‌های Python ما

در پروژه‌های <span dir='ltr'>`01-port_scanner`</span> و <span dir='ltr'>`02-dns_lookup`</span> ممکن است در حال حاضر به API Key یا رمز عبور نیاز نداشته باشیم.

بااین‌حال، این اصول در توسعه نسخه‌های بعدی و ابزارهای جدید اهمیت پیدا می‌کنند.

برای مثال، اگر در آینده ابزاری بسازیم که با یک سرویس امنیتی خارجی ارتباط برقرار کند، باید:

<p dir='rtl'>
• API Key را از کد جدا نگه داریم. <br>
• تنظیمات لازم را از محیط دریافت کنیم. <br>
• از ثبت کلید در Logها جلوگیری کنیم. <br>
• در صورت امکان، کلید را به حداقل مجوز لازم محدود کنیم. <br>
• رفتار برنامه در نبود کلید را به‌درستی مدیریت کنیم. <br>
• برای محیط توسعه و عملیاتی تنظیمات مناسبی داشته باشیم.
</p>

اگر ابزار ما فقط به یک مقدار تنظیماتی غیرمحرمانه نیاز داشته باشد، نیازی نیست آن را بی‌دلیل Secret تلقی کنیم. تشخیص درست نوع داده نیز اهمیت دارد.

## ۱۳. اشتباهات رایج

### اشتباه اول: قرار دادن API Key داخل کد

کلید ممکن است همراه کد منتشر یا در تاریخچه Git باقی بماند.

### اشتباه دوم: تصور اینکه <span dir='ltr'>`.gitignore`</span> فایل‌های قبلی را پاک می‌کند

این فایل فقط بر دنبال کردن فایل‌ها توسط Git اثر می‌گذارد و تاریخچه قبلی را پاک نمی‌کند.

### اشتباه سوم: حذف Secret افشاشده بدون تعویض آن

اگر کلید قبلاً منتشر شده باشد، باید آن را لغو یا تعویض کرد؛ حذف فایل به‌تنهایی کافی نیست.

### اشتباه چهارم: ذخیره رمز عبور به‌صورت متن ساده

در صورت افشای پایگاه داده، رمزها مستقیماً در اختیار مهاجم قرار می‌گیرند.

### اشتباه پنجم: استفاده از SHA-256 ساده برای ذخیره رمز عبور

برای این کار باید از الگوریتم‌های تخصصی مشتق‌سازی کلید از رمز عبور استفاده شود.

### اشتباه ششم: چاپ Secret در Log

حتی اگر مخزن کد امن باشد، Logها نیز می‌توانند به مسیر افشای اطلاعات تبدیل شوند.

### اشتباه هفتم: دادن مجوز بیش‌ازحد به API Key

اگر کلید به خطر بیفتد، مجوزهای بیش‌ازحد می‌توانند خسارت را افزایش دهند.

### تمرین اول: بررسی یک قطعه کد

کد زیر را بررسی کن:

```python
import requests

API_KEY = "example-secret-value"

response = requests.get(
    "https://api.example.com/data",
    headers={"Authorization": f"Bearer {API_KEY}"},
    timeout=10,
)

print(response.text)
```

به این پرسش‌ها پاسخ بده:

۱. چرا قرار دادن کلید در کد می‌تواند خطرناک باشد؟

۲. چگونه می‌توان کلید را از متغیر محیطی دریافت کرد؟

۳. آیا چاپ کامل پاسخ همیشه مناسب است؟ چه اطلاعاتی ممکن است در پاسخ وجود داشته باشد؟

۴. چرا باید برای درخواست HTTP از Timeout استفاده کنیم؟

توجه: دامنه `example.com` در این مثال صرفاً نمونه است و این کد به‌تنهایی یک سرویس واقعی را پیاده‌سازی نمی‌کند.
